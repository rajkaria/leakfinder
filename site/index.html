How it works

Three things to check

Give LeakFinder a Postgres and a Stripe key. The agent works out your schema, writes the reconciliation, and writes the fix.

1

It writes and fixes its own code, in a sealed room.

The agent has never seen your schema. It writes Python, runs it in a CreateOS micro-VM and reads what comes back. When a query fails, it reads the error and rewrites the script. Nobody is typing.

The VM can reach api.stripe.com and your database host. Everything else is dropped by a rule on the host, outside the VM, so code inside cannot change it.

  • api.stripe.comallowed
  • your database hostallowed
  • anything elsedropped
2

The model never sees a customer.

It gets code, schema, counts and errors. Emails are redacted before any text reaches it, and the findings go to a file inside the VM, not to the model. Every byte the model was shown is saved in a transcript you can grep.

Take a customer email from the report and search for it in that transcript. The count is the proof. The guard redacts email addresses; other fields stay out because the agent's scripts are asked to print counts only.

# an email from the report
$ grep -c "<email>" transcript.jsonl
0

The live demo runs this check with the email the seed plants.

3

Apply closes the leak, in Stripe test mode.

The agent writes the fix script too. It dry-runs first and prints a plan with counts. A person presses Apply: invoices out, refunds issued, access revoked, rows synced.

Then a separate program reads Stripe and Postgres directly, without the agent, and reads zero. Apply runs with a Stripe test key only. Invoices are sent, not collected.

  1. Dry runA plan with countsNothing changes in Stripe or the database.
  2. ApplyInvoices, refunds, revokes, syncsIn Stripe test mode, after a person clicks.
  3. VerifyZero, zero, zeropnpm run verify counts the drift again from Stripe and Postgres.

The sealed room

The code runs next to the data. The model stays outside.

Your laptop runs the LeakFinder CLI. It passes Python into a CreateOS micro-VM and passes back only what the script prints, with emails redacted, to the model.

What it finds

Three ways Stripe and your database drift apart

A missed webhook is enough. Stripe cancels someone and the app never hears, or someone pays and never gets an account.

DriftWhat is wrongIn the demo datasetWhat Apply does
APro access nobody pays for The app grants Pro. Stripe has no active or trialing subscription for that user. 12 users7 never paid, 5 cancelled in Stripe while the app never heard Revokes the access and sends a one-month invoice, due in 7 days.
BPaying with no account Stripe has an active subscription for a customer no app user owns. 3 payerscharged every month, with no account to use Refunds the latest payment and cancels the subscription.
CRows out of sync The app's subscription row says active. Stripe says canceled. 5 rowsthe same 5 users Stripe cancelled Sets the app row to Stripe's status.

Pro is $29 a month in the demo dataset: 12 × $29 = $348 a month leaking. These are the seed's answer key. A separate check, pnpm run verify, recounts them from Stripe and Postgres.
